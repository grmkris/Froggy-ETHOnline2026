# Design: ENGINEERING-FIRST: ship a hosted, judge-clickable product in 9 days with 2-3 peo

**Angle:** ENGINEERING-FIRST: ship a hosted, judge-clickable product in 9 days with 2-3 people. Every decision below is chosen for the smallest verified path that still qualifies all five tracks. One person owns Chrome full-time; the wallet slice is built on the Privy Telegram recipe verbatim; the Hedera leg is honest lunch money; Graph data comes from a Studio key first and x402 second; everything runs on one Hetzner box behind Caddy from Day 0, not Day 6. Hard cut lines are dated and named.

**Names:** Handrail (a rail you grab; the browser is the rail, the policy is the grip); Lunchbox (the agent's lunch-money pocket plus the box you watch it in); Pocketwatch (watch the pocket, watch the page); Tandem (one Chrome, two riders, one brake); Sidecar (the wallet rides beside the browser, human holds the handlebars) -- avoid 'Leash' (hms1499/leash shipped this week on Celo) and 'Tether' (AgentTether is an ETHOnline peer)

**One sentence:** A web workspace where you and your AI agent share one hosted Chrome you can watch, grab and freeze, and the agent pays for what it finds from a prefunded pocket that Privy policy (EVM leg) and a serialized host ledger (Hedera leg) cap, with The Graph's standardized lending data deciding what is worth buying and Hedera x402 via Blocky402 as the rail it buys on.

**Tagline:** One Chrome for you and your agent. A pocket it can spend. A policy it cannot talk its way around.

**20s pitch:** Every agent wallet gives a model a key and a cap. We give it a browser you can see. You watch the page it is on, you can take the mouse, and you can freeze it. It pays from a pocket: on the EVM leg Privy's policy engine holds the per-transaction cap, the daily cap and the recipient allowlist even if you jailbreak the prompt; on Hedera the pocket is host-capped lunch money that can only be filled through that Privy policy. The Graph tells it the cheapest USDC borrow across Aave and Compound; it buys the packed report from an x402 service we host on Hedera, settled by Blocky402; you get the HashScan tx, the HCS receipt and the policy id that allowed it. Testnet, open source, live at a URL you can click right now.

**Daily job:** The one job the product does daily in this build: re-run the user's saved Graph question ('cheapest USDC borrow across N protocols'), buy the packed report over Hedera x402 only if the answer moved (freshness gate on block number), and page the human on Telegram with the receipt (deployment ids + block, Hedera tx id, HCS message, policy id, pocket balance). Everything else (browse, grab, freeze, top-up) is the session job. The scheduled re-run is a 2h cron on D6 and is the first thing cut; without it the product is a one-shot demo and we say so.

**Custody and policy:** KEYS (four, named in code exactly like this):
1. W_user -- Privy embedded EVM wallet per user (secp256k1 EOA), owner = the Privy user created from telegram_user_id. The agent is an additional_signer: a host-held P-256 authorization key AGENT_SIGNER with override_policy_ids [P_agent]. The model never sees any key; it calls host tools.
2. K_pocket -- one Hedera testnet ECDSA account per user, created by the host at /start (AccountCreateTransaction from K_treasury, 5 HBAR seed), private key AES-256-GCM encrypted in SQLite under a server KMS key. It signs x402 TransferTransactions through @x402/hedera createClientHederaSigner (pin one node: client.setMaxNodesPerTransaction(1)). Privy has ZERO policy coverage here (raw sign is not in Privy's policy method enum; Hedera is Tier 1), so the host enforces the caps.
3. K_treasury -- host Hedera ECDSA account (portal.hedera.com) + a Privy server wallet on Base Sepolia. Prefunds pockets. Not reachable from any agent tool.
4. Service side -- payTo account 0.0.Y (a real 0.0.x id, aliases are rejected by the scheme), HCS topic 0.0.Z for receipts.

P_agent (default DENY, JSON in repo, tested by a deny-suite on D3):
 a. eth_signTransaction, chain_id 296 (Hedera EVM via Hashio): ALLOW iff ethereum_transaction.to in condition_set 'pockets' (the user's own K_pocket alias) AND value lte 2 HBAR AND aggregation(sum value, 86400s) lte 10 HBAR. This is the top-up. Host broadcasts via Hashio. If the D1 spike shows Privy cannot sign on 296, fallback rule a': same shape on chain 84532 for a USDC transfer to K_treasury (calldata transfer.to in 'payees', transfer.amount lte 2 USDC, 24h sum lte 10 USDC) and the treasury credits HBAR to the pocket ('OTC desk', documented as mocked bridge).
 b. eth_signTransaction, chain_id 84532: USDC transfer with calldata transfer.to in 'payees' (server-issued recipients only), amount lte 2 USDC, 24h aggregation lte 10 USDC. This is what 'send the rest to 0xevil' hits and is denied by Privy, not by the model.
 c. (stretch, D6) eth_signTypedData_v4: domain.chainId == 84532 AND verifyingContract == 0x036CbD53842c5426634e7929541eC2318f3dCF7e AND TransferWithAuthorization.value lte 20000 AND .to in 'payees'. Only exists if the Base Sepolia rail on our service ships. Daily cap for this lives in the host ledger because Privy aggregations do not cover typed data.
 d. Session expiry: system.current_unix_timestamp lte session_end on every ALLOW rule (policy regenerated per session, 24h).
 We use eth_signTransaction + host broadcast, never eth_sendTransaction, because rolling aggregations only apply to signTransaction/signUserOperation.

WHERE EACH CAP IS ENFORCED (say this table in README):
 per-tx cap: W_user -> Privy (policy); K_pocket -> host ledger (checked BEFORE signing).
 daily cap: W_user eth_signTransaction -> Privy aggregation (racy: updated after signing, so the host also serializes W_user signs with a per-user mutex); K_pocket and any typed-data -> host ledger, serialized per user.
 recipient allowlist: W_user -> Privy condition set 'payees'/'pockets' (server-issued ids only); K_pocket -> host allowlist of 0.0.x payTos (our service + registered peers).
 expiry: Privy timestamp condition + host session TTL.
 Ledger: SQLite table spends(user, leg, amount, state, payment_id, tx_id, ts); daily = rolling 24h sum in state in {signed, settled}.

KILL SWITCH SEMANTICS (one function, freeze(user, reason)): (1) set users.frozen_at (checked before EVERY Privy call and every pocket sign; Privy access tokens can live 15 min so the flag is the real gate), (2) abort the active run (server-owned AbortController, not req.signal), (3) privy.wallets().removeSigners(W_user, [AGENT_SIGNER]) (immediate), (4) wipe K_pocket ciphertext (pocket_killed_at) and sweep remaining HBAR to K_treasury, (5) Telegram message with reason and a 'new session' button that re-creates a pocket (new key) and re-adds the signer. Unfreeze is a human action in the web app or Telegram, never a tool; resolvePermission / raise_limit / unfreeze are not in the tool list. Approval above cap: Telegram inline buttons, callback_data = server nonce, TTL 5 min, callback_query.from.id must equal the bound telegram_user_id; free text is never an approval.

**Architecture delta:** Changes vs ARCHITECTURE.md/PLAN.md, each with hours:
1. Custody split (0h to decide, 6h to build): 'Privy policy is the leash on the Hedera x402 payment' is false. Hedera leg = per-user host-held ECDSA pocket with host caps; Privy gates only EVM signatures. Do NOT build the Privy-raw-sign Hedera signer (8-12h, zero policy value).
2. Daily cap mechanics (2h): eth_signTransaction + host broadcast instead of eth_sendTransaction so Privy's rolling aggregation actually applies; typed-data and pocket daily caps in a serialized host ledger.
3. Browser: worker-per-user Bun.WebView (verified in Docker; +1 day) instead of 'dataStore per user' (verified ignored). Bun 1.4.1 (close() fix). All CDP goes through packages/browser/CdpTransport (send/on, ~40 lines) so puppeteer-core is a transport swap, not a rewrite. Single tab only: override window.open to same-tab navigation. 40h Chrome slice total.
