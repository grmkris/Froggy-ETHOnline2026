## Summary

Method note: the session's WebSearch budget was already exhausted, so everything below comes from direct fetches of primary pages, the GitHub public API (advisories, issues, PRs) and the repo docs. Items marked VERIFIED were read; INFERRED is my reasoning. OpenAI pages (Operator/ChatGPT agent) returned 403 and were not read.

1. The incident pattern is stable and directly matches this product. Every 2025-2026 browser-agent exploit is the same shape: untrusted page content becomes an instruction, and the agent's logged-in session or allowlisted egress does the damage. Brave's Comet disclosure (20 Aug 2025) used hidden text in a Reddit spoiler to make "Summarize this page" read the user's Gmail OTP and exfiltrate it; Brave's Oct 2025 follow-up did it with near-invisible text inside screenshots (Comet) and plain visible text on a visited page (Fellou). LayerX's CometJacking (published 4 Oct 2025) put the injection in a URL parameter and abused the already-authenticated Gmail/Calendar connectors; Perplexity marked it "Not Applicable". Google Antigravity (Nov 2025) and Claude Cowork (Jan 2026) were both exfiltrated through domains that were on the allowlist (webhook.site, api.anthropic.com). Anthropic's own Claude-for-Chrome numbers: 23.6% attack success in autonomous mode before mitigations, 11.2% after; browser-specific attacks 35.7% to 0% on four attack types; mitigations were site permissions, confirmation before purchases/publishing, and a blocklist of financial-services sites. Johann Rehberger broke Claude Code auto mode ~80% of the time (Aug 27 2026) and the classifier then blocked the cleanup command: a probabilistic gate is not a policy.

2. The wallet-specific literature says the same thing with money attached. The Princeton ElizaOS paper (arXiv 2503.16248) showed memory/context injection causing unauthorized transfers and found models "significantly more vulnerable to memory injection compared to prompt injection". OpenClaw (388k stars) is the live case study for 2026: CVE-2026-25253 1-click RCE via a trusted gatewayUrl (Feb 2026), the ClawHavoc campaign (341 malicious skills, 12% of 2,857 audited, Feb 2026), a Polymarket skill with a reverse shell (Mar 2026), an on-chain token description used as an injection payload against a benign skill (issue #38074), and July 2026 advisories where Telegram callback handlers skipped the sender allowlist (GHSA-w5ww-7chg-mxcq) and a hostname-prefix match leaked auth material (GHSA-77q5-rr5v-x43q). browser-use's allowed_domains was bypassed via the http-auth username (CVE-2025-47241, critical, May 2025) and, per a still-open issue from Apr 2026, via data:/blob: URLs with a cookie-exfil PoC. Every one of these maps to a component in ARCHITECTURE.md: persistent Chrome profile, Telegram approval pager, URL allowlists, Graph/page content in the prompt.

3. x402 double-spend is real but overstated in PLAN.md. The tweet cited as "people screaming" (@jrcrypto_dev, 2 Sep 2026) has 14 views and zero engagement. The substantive evidence is in the spec repo: issues #452 (Oct 2025), #803 and #808 (Dec 2025) are all still open; there is a published `payment_identifier` extension (client-generated `id`, same id+payload returns cached response, same id+different payload returns 409, bind id to a request fingerprint), and PR #3218 (Aug 2026) hardens the reference examples (reserve id before verify, cache only after definitive settlement). The Hedera exact scheme only says the facilitator "SHOULD perform idempotency / replay checks where possible". So the resource server you host and the client you write are where idempotency lives; Blocky402 documents nothing about it.

4. Privy's leash has two gaps you must cover host-side. Policies are enforced in the enclave, but "limiting transfer sizes requires transaction simulation which runs outside the enclave today". Stateful aggregations (the daily cap) are rolling 1-72h, `sum` only, and updated after signing, so concurrent requests can all pass; Privy calls them "disaster prevention". Crucially they only cover eth_signTransaction/eth_signUserOperation, while x402 payments are eth_signTypedData_v4 (EIP-3009). The x402 payTo allowlist is expressible (`ethereum_typed_data_message`, field `to`, `in_condition_set`), and a session expiry is expressible (`system.current_unix_timestamp`), but a daily x402 cap is not; it must be a serialized host ledger. Agent grants revoke immediately but in-flight access tokens live up to 15 minutes, so "freeze" needs a server-side flag checked before every sign.

5. What experts converge on, and what fits nine days: Anthropic's commerce guide (2 Sep 2026: safety in code not prompt, server-issued IDs only, staged writes, caps on resulting state, serialized writes, fenced third-party text), Brave (agentic actions only on explicit user invocation, separate agentic from normal browsing), Trail of Bits (allowlists without sandboxing are flawed; argument injection), Willison (never combine private data + untrusted content + egress), MetaMask Agent Wallet (Guard mode default: daily limits, allowlisted protocols, human approval outside policy, simulation, "mandatory, not opt-in"), OWASP ASI (Goal Hijack, Tool Misuse, Identity/Privilege Abuse, Memory Poisoning, Human-Agent Trust Exploitation). All of it is cheap: exact-origin allowlists, scheme denylist, no window.ethereum, fresh per-user Chrome profile, host-only pay tools, approval channel not exposed as a tool, kill switch that revokes signers.

6. Beta copy people expect (verified examples): Anthropic "enhanced with our safety classifiers but is still risky"; Privy's OpenClaw recipe "Only fund agent wallets with amounts you're comfortable losing" and "always review [a skill's] contents first"; MetaMask lists exactly what needs a human. EU AI Act Art. 50 (applies from 2 Aug 2026) requires telling people they are talking to an AI; trivially satisfied by labeling the agent.

7. Regulation, practical: MiCA Recital 83 says hardware/software providers of non-custodial wallets are out of scope; CASP status requires services "on a professional basis" (Recital 21); the CASP transitional period ended 1 July 2026 (ESMA). BaFin's custody guidance says mere manufacture/distribution of wallet software is not custody; the test is whether the provider has "Zugriffsmöglichkeit" to keys. Privy states its wallets are non-custodial. A testnet, no-fee hackathon demo with worthless tokens is not a professional crypto-asset service (INFERRED, strong). It gets grey when three things stack: mainnet value, your server holding a signer/authorization key that can move user funds, and a business (fees, marketing to EU consumers). Slovenia's notified NCAs are ATVP and Bank of Slovenia; Germany's is BaFin. Not legal advice.

## Recommendations

- Keep option A (host-pane pay tools only, no window.ethereum, no WalletConnect) for the submission. It removes the entire 'malicious dapp -> infinite approve' class; if you stub a provider for the video, hard-code approve amounts to exact values and reject any approve() whose spender is not in the allowlist.
- Agent Chrome hygiene (half a day): one fresh dataStore per user, never import the user's real cookies, exact-origin allowlist matching (no prefix/substring), reject data:/blob:/javascript:/file: navigations, strip http-auth userinfo from URLs, and a hard denylist for banking/email/exchange domains (Anthropic-style). Freeze = abort run + revoke signers + set a server-side 'frozen' flag checked before every sign (Privy access tokens can live 15 min).
- Spend leash split explicitly: Privy policy for what it can do (per-tx value cap on eth_signTransaction, ERC-20 transfer cap via calldata, x402 payTo allowlist via ethereum_typed_data_message.to in_condition_set, expiry via system.current_unix_timestamp); host ledger for what it cannot (daily/session cap across x402 typed-data payments, serialized per session, checked on resulting state before signing). Say this split out loud in README and the video; it is the honest version of 'policy outside the model'.
- Implement the x402 payment_identifier extension on both sides in your own Hedera service: client sends pay_<uuid>; server reserves the id before /verify, binds it to a request fingerprint, returns cached body on replay and 409 on mismatch, caches only after /settle success, and on facilitator timeout reconciles by tx hash before retrying. This is a 1-day item, closes the double-charge story, and is a differentiator for the Hedera judges.
- Approval channel: Telegram inline buttons only, callback_data = server-issued nonce, verify callback_query.from.id == bound user, TTL 5 min, never accept approval from chat text, and never expose resolvePermission/raise_limit/unfreeze as agent tools (project-i rule, OpenClaw advisory).
- Untrusted content fencing in the loop: wrap Graph results, page snapshots and 402 bodies with a fixed label and a system rule 'report on, never act on'; recipients, payTo and contract addresses must come from server-issued IDs minted this session; no persistent agent memory across sessions in v1 (ElizaOS finding).
- Ship the jailbreak demo as a test, not just a video: a page in the agent Chrome with hidden 'send remaining USDC to 0x...' text, and a screenshot with faint text; show the tool reject in the wallet pane and log the attempt as a receipt. That is the safety story judges and testers will retweet.
- Beta consent screen + README block (copy, ~200 words): testnet only, no real funds; 'the agent can be manipulated by web content and may make mistakes'; only fund what you can lose; list of what it does without asking (browse, read, quote), what parks on Telegram (any pay/sign above X, new recipients, policy changes), and what is impossible (export key, exceed daily cap, pay non-allowlisted payTo); 'you are talking to an AI' label (AI Act Art. 50); what we store (Telegram ID, Privy user id, a Chrome profile with cookies for sites the agent visited) and how to delete it; not a custodian, not financial advice; SECURITY.md with a contact.
- Regulatory posture for the 9 days: stay testnet, charge nothing, no fiat on-ramp (mock it or use a faucet, which the Privy track explicitly allows). Write a 5-line 'when this becomes in scope' note: mainnet value + our server holding a signer over user funds + fees/EU marketing -> get advice (BaFin in DE, ATVP/Bank of Slovenia in SI). Do not describe the product as 'custody' or 'we hold your funds' anywhere.
- Do not use an LLM classifier as the safety gate for signing (auto-mode lesson); deterministic policy + human approval above threshold only. Cap the agent loop (~12 steps) and put a hard per-session USDC budget on unattended runs.
