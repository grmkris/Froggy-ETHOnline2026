## Findings fixed

| Finding | User impact | Change and evidence |
| --- | --- | --- |
| Account deletion ignored the HTTP status. | A failed deletion reloaded the app as though it succeeded; network failures had no usable recovery. | Reload only on success. Keep the confirmation open with pending, error and retry states. Browser regressions cover HTTP failure, network failure and successful retry. |
| Service results were focused before returning to the catalog. | On mobile, the catalog pushed the newly focused result below the viewport. | Focus and scroll after the route's catalog layout commits. The walkthrough now asserts that the result heading is in view without scrolling on the test's behalf. This assertion failed on the previous implementation. |
| Digest failures were hidden while the digest was off. | Enabling a digest could fail without feedback; an initial load failure looked like “Off.” | Show save errors independently of the saved hour. An unknown setting is disabled and labeled unavailable, with a reload action. Tests cover failed enable, retry, persistence after reload and failed initial loading. |
| The services page nested two columns inside a 768px page. | Desktop cards were narrow, long action labels clipped, footers did not line up, and the empty task panel stretched to the catalog's full height. | Widen the page, delay the side-by-side task layout until there is space, align card actions, and keep the task section at its natural height. Check both the viewport and the internal scrolling container for overflow. |
| Amber status text used the same bright color as driving indicators. | Small simulated/pending labels were difficult to read. | Add a darker semantic text token. Preserve the amber driving rings and backgrounds. |
| Screen tests only captured the first viewport. | Settings and service content below the fold was missing from the visual evidence; console errors were not checked. | Capture overlapping scroll sections, check console and page errors, add 320px coverage, and capture interaction states. One-time connection tokens and OAuth codes are masked. |

## Design changes

The existing warm paper, green accent and Bricolage/Onest typography remain. Desktop navigation now has readable horizontal labels; tablets retain the compact rail and phones retain five bottom tabs. Page headings and spacing have a clearer hierarchy. Services, agent connections and settings use the available desktop width. The chat welcome introduces the agent and offers three compact actions; the wallet has a clearer balance panel and activity state.

No dependencies were added. Wallet authority, OAuth permissions and browser arbitration were not changed.

## Browser evidence

Interaction captures include funding, wallet balances, service requests/results, agent instructions and connections, deletion confirmation, scheduled reminders, OAuth consent/manual completion, chat approvals/receipts, and inline/split/pop-out browser layouts.

Run `bun run e2e --workers=3` to reproduce the screenshot set in `test-results/`. The capture helpers wait for fonts and walk the application's internal scroll container; a normal full-page screenshot alone cannot see all of it.

The browser environment uses explicit stubs and local identities. These captures establish responsive Chromium behavior, not physical-device testing, live Privy funding, paid supplier delivery, Telegram delivery, or a live shared-Chrome screencast. OAuth consent and revocation are exercised against the local authorization server. The additional capture states do not involve real payments.
