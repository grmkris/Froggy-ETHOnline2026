# 0038 — Credit purchases signed in the person's browser; no owner signing on the server

Date: 13 September 2026. Status: accepted and built, gates green; the first browser-signed purchase on production is still to be recorded in `docs/evidence/PRIVY.md`.

Buying credits with USDC on Base failed on production with `Privy rejected the signing request: 400 {"error":"Invalid JWT token provided","code":"invalid_data"}`. The pay route handed the person's Privy access token to Privy as `authorization_context.user_jwts` and asked it to sign the x402 authorization with their embedded wallet. Privy has refused that exchange on this app for every user since 7 September (`docs/evidence/PRIVY.md`). The app is already in TEE mode and has no custom JWT provider, so there was nothing to switch on: the only "server-side" setting Privy offers lives inside its bring-your-own-identity-provider integration, which this app does not use. Privy's own pattern for apps that log in with Privy is that the person signs in the browser with the client SDK, which this app already did live for the agent-signer consent and for sponsored batch trades. The owner decided, the same day: no server-side owner signing, ever, and one click rather than a second Privy prompt. Building the other two owner-signed flows on browser signing, and the Solana wallet wording on the purchase panel, are outside this decision.

## The browser is the x402 client for its own purchase

The review step's Confirm asks the server for the frozen quote (`GET /api/credits/purchases/:id/pay`, a 402), builds the EIP-3009 `TransferWithAuthorization` from that quote and nothing else, signs it with the person's Privy embedded wallet through `useSignTypedData`, and posts the x402 header as `payment-signature`. The pieces the browser needs, the challenge schema, the typed-data builder, the nonce and the header encoder, are pure functions in `packages/protocol`, because the web app may not import the payments package and pulling the x402 SDK into the bundle for one struct would bring viem and zod with it. The `EIP712Domain` type is listed because the wallet RPC wants it; a server test pins that the digest equals the one the x402 facilitator verifies without it. The authorization's end of validity is the quote's expiry plus the offer's window, anchored to the server's clock so a slow browser clock cannot produce a signature that is claimed and then refused at settlement.

The server's existing `accept` path pins the header's accepted terms to the quote and requires the paying address to be the person's Privy Ethereum wallet, read with the app secret. It now also refuses an expired quote before reading the header and, for an unpaid quote, recovers the signer from the signature and checks the window (`verifyCreditAuthorization` in `packages/payments`) before claiming, so a bad signature leaves the quote signable instead of claimed and failed. Settlement is unchanged: the facilitator verifies the signature again, contract accounts included, and the treasury broadcasts `transferWithAuthorization` and pays the gas. The body path that used to sign on the server answers `signature_required` with a sentence for a live USDC quote; stubbed quotes and HBAR quotes keep it, since the server holds what those need.

## What was removed

The owner signers (`privyOwnerSigner`, `privyOwnerTransactionSigner`, the EVM, trade and Solana factories) and the `PrivyServer` members that exposed them are deleted, with their tests. The wallet PATCH that revoked the agent signer went through the same refused exchange and had had no caller since the browser took over granting; it is gone too. The access token no longer travels into the credit pay route, the purchase answer route, the trade answer route or the card checkout approval; those routes were already owner-authenticated and nothing signed with the token any more. What remains of owner authentication in the wallet package is the DID match that guards Solana wallet creation, which uses the app secret and verifies the token locally.

Two flows still depended on owner signing and now say so instead of failing somewhere vaguer. A bound-URL purchase on Base or Solana fails after approval with: paying from your USDC or Solana wallet needs a signature from your browser, which this purchase flow cannot ask for yet; pay with HBAR, or wait for browser signing here. A Solana or single-transaction trade approval is refused with a `trade.signer` sentence saying the same; sponsored batch trades, which already sign in the browser through the managed-execution authorization, are unaffected. Neither flow reached a signature on production before this change either.

## One click, and what it costs

Privy's own confirmation modal is hidden for this signature. The person sees Froggy's review step, with the exact amount and the recipient, and a sentence saying that confirming asks their wallet to sign one USDC transfer to Froggy for exactly that amount and that Froggy pays the network fee. The typed data is built only from the server's quote inside one function; the server refuses any header whose terms, signer or window differ; the page's Content Security Policy is strict. The residual risk is that a compromised page could ask the key to sign something else, since the person's own key is under no Privy policy. The per-action flag is one line to flip, and Privy's dashboard can force its modal on without a code change. If Privy shows the modal anyway because of that dashboard setting, that is acceptable and gets recorded, not fixed.

## Follow-ups

Bound-URL purchases on Base and Solana, and Solana and single-transaction trade approvals, on the same browser signing primitive (`Identity.signTypedData`, plus a transaction signer for Solana). The purchase panel still offers to create a Solana wallet for a payment it cannot yet sign. `AgentGrantRequest` still carries the access token that the grant no longer uses; the server threads it through `grants.ts` for nothing. The first production purchase: one USDC on Base, the `credit funding <id>: confirmed 0x…` line in the Railway log, the `transferWithAuthorization` from the treasury on Basescan with one transfer from the person's address, and whether Privy showed a prompt.

## Rejected

Signing with the agent signer under its policy: a credit purchase is the person spending, and it would require every buyer to have consented first. The `signPrivyRequest` relay the batch trades use: it exists to let the server drive a Privy REST call the browser cannot make; a plain typed-data signature needs no relay and no app secret in the loop. The x402 SDK in the browser: the boundary forbids the import and the bundle cost buys nothing. A browser-clock validity window. Answering the old body path with a 402: a cached bundle would render the generic error rather than the challenge. Enabling Privy's JWT integration: it is for apps that bring their own identity provider, would make users custom-auth accounts distinct from their Google logins, and would let the server move the whole wallet under no policy for the token's lifetime.
