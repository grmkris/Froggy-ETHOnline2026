# 0028 — User email belongs to conversations

Each authenticated person may claim one permanent handle on the configured email domain. A disabled or deleted mailbox keeps its handle reserved. Email is optional and included; model and browser execution retain their existing charging and approval rules.

Unmatched mail goes into a system-created Email conversation. Replies use a draft-specific Reply-To alias or match prior Message-ID references; task aliases correlate a short active wait with its originating conversation. Incoming content and attachments are untrusted data. They cannot grant spending authority, expand a task, or approve an outgoing message. Late delivery posts a notice and offers a human Continue action; it does not start another agent run.

Postgres owns mailbox identity, quotas, parsed messages, file metadata, draft revisions, send attempts and waits. Cloudflare Email Routing receives raw messages into private R2 storage and queues a signed ingestion notification. The server parses the message, stores owned files and commits a recipient-bound digest before acknowledging ingestion. Delivery events enter through another queue. Every gateway request signs method, path, timestamp and body hash.

Sending is a human-only API operation on an exact draft revision, including recipients, body and attachment hashes. The server commits the attempt and quota reservation before invoking the Worker. A Durable Object keyed by draft ID persists a claim before calling Email Sending. Replays return the recorded provider ID or an uncertain result, never another provider call. Maintenance recovers recorded acknowledgements through a read-only lookup. There remains an unavoidable uncertain window if the provider accepts but the Durable Object cannot record its response. Such attempts require operational investigation; they are never automatically resent.

Connected agents need an explicit `email:read` grant for the entire mailbox, and a separate `email:draft` grant to create documents and drafts. Existing grants, legacy unrestricted tokens and omitted OAuth scopes gain neither permission. There is no send or approve tool. Email tool inputs and outputs are redacted from generic activity/history records. Requested images and scanned PDF pages enter the ordinary model turn, with its normal accounting, or are returned to a connected agent with explicit email-read permission. The owner explicitly authorized those destinations on 12 September 2026.

Files are private downloads. Text/PDF extraction is bounded; PDF work runs in a separate Bun process with a time limit, capped raster dimensions and a capped result. HTML is reduced to inert text; external images are not fetched. PDF and text document generation use a bundled licensed font. Unsupported formats remain download-only.

The initial limits are 1 GiB per mailbox, 25 recipient deliveries in a rolling 24-hour window, 25 MiB per incoming message and a conservative 5 MiB encoded outgoing limit. Deletion clears bodies and tombstones records before asynchronous object cleanup; maintenance retries cleanup after restart. Minimal metadata remains for deduplication, handle reservation and send accounting. Deleting a conversation does not reset the sending quota.

Local loopback development uses explicit `froggy.test` stubs. Other environments expose email only with complete configuration and a durable database. Stub mail, files and drafts are visibly marked and never imply real delivery. Production setup and verification are documented in [the email runbook](../EMAIL.md).
