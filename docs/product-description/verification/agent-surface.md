# Verification: agent surface

How to run this file: the "user" here is a piece of software, so almost every item is a command rather than a click, and the whole file can be worked through from one terminal beside one browser tab. **The base URL** is the deployment under test — the Railway origin for a pass that means anything about money, or `http://localhost:3001` after `bun run dev` (the server's `PORT` defaults to 3001; the web app is on `APP_ORIGIN`, `http://localhost:3000`, and `/mcp` lives on the server). Export it as `FROGGY` and check `GET $FROGGY/health` first: it reports each integration as `live` or `stub`, and that reading decides which rows can pass and which are `blocked (stub)`. **A token** comes from one of three places, and they are not interchangeable: (1) a real grant — sign in with the CLI (`curl -fsSL "$FROGGY/froggy-cli.js" -o /tmp/froggy.mjs; node /tmp/froggy.mjs login --url="$FROGGY"`), click **Allow** on the consent screen, then read `~/.config/froggy/credentials.json` with `jq -r .accessToken`; (2) a grant with hand-picked scopes — register a client with `POST /oauth/register`, drive `/oauth/authorize` in the browser, turn off the switches the row asks you to, and exchange the code (rows that need this say which scopes to leave on); (3) a minted `fgy_` token from the Connections page, which is **null-scoped** and must never be used for a scope row, only for the rows that are about it. Never put a token in a URL. Device values: `curl` — any HTTP client, no Froggy account state needed beyond the token the row names; `CLI` — the downloaded `froggy` bundle run with `node`; `a connected agent` — a grant that actually went through the consent screen, with the scopes the row names (a minted token is _not_ this condition); `browser` — the person's own signed-in browser at 1440px, needed for the consent screen and the Connections page; `live credentials` — `/health` reports the relevant integration `live`. **Anything that needs real money or a real Hedera transaction records `blocked (stub)` on a stubbed build**, never `pass` — see [the rule that overrides the usual protocol](README.md#the-rule-that-overrides-the-usual-protocol).

Two helpers the rows assume are defined:

```sh
export FROGGY=https://froggy.example        # or http://localhost:3001
export TOKEN="$(jq -r .accessToken ~/.config/froggy/credentials.json)"

mcp() {   # $1 is the JSON-RPC body; prints the status line, the headers and the body
  curl -sS -i -X POST "$FROGGY/mcp" \
    -H "authorization: Bearer $TOKEN" \
    -H 'content-type: application/json' \
    -H 'mcp-protocol-version: 2025-06-18' \
    --data "$1"
}
```

## What this file deliberately does not cover

- **The person's side of every screen it touches.** The consent screen's rendering at 390px, its 44px targets, the announced refusals and the theme are [workspace](workspace.md) and [cross-cutting](cross-cutting.md) concerns; only the rows where the agent's behaviour depends on them appear here.
- **The leash's own rules.** The codes are checked from the agent's side — what it reads and what it should do next. The ordering, the rolling window's arithmetic, the receipt's construction and the action-kind table belong to `foundations/the-leash.md` and its own checklist, including [B-02](../bug-triage.md#b-02-the-action-kind-authority-table-is-never-consulted-so-transfer-and-trade-do-not-always-ask) and [B-03](../bug-triage.md#b-03-editing-your-allowance-does-not-reach-froggys-own-mandate), which are referenced from REFUSE-20 rather than owned here.
- **The trading surface.** The six trading tools appear only as scope evidence (CONSENT-12, PAID-07). What they do, what they cost and what they preserve as unknown is `workspace/trades.md`.
- **Connections as a page.** Rows read the invocation trail to confirm something was recorded; the list, the detail page and disconnecting are `workspace/connections/*`. [B-06](../bug-triage.md#b-06-a-minted-token-is-displayed-as-holding-fewer-scopes-than-it-actually-has) is checked here from the token's side (CONSENT-04, REFUSE-03) because the reach is the agent-surface fact; the page's own copy is checked there.
- **Bug-triage entries not raised by an agent-surface document.** B-01 (REFUSE-01) is the one exception, because `being-refused.md` says the `frozen` question "matters more than anything else on this page".
- **Load, concurrency and rate.** PAID-06 asks whether polling is throttled at all; nothing here measures throughput, latency or behaviour under many connections.
- **The stubs themselves.** Whether a stub is loud is `cross-cutting/stubs.md`; READ-18 only checks that `stubbed` reaches the agent in the data.
