# Home + Watchlist: implementation gap assessment

Assessed 12 September 2026 against the current worktree, including uncommitted changes.

Targets: [mobile Home / Watchlist / details](01-mobile.png) and [desktop Home with optional Watchlist](02-desktop.png). These replace the earlier Markets / Portfolio / Browser concept. This assessment answers what is missing; it does not claim the UI or new monitoring features have been implemented.

**Conclusion:** The existing app supplies the conversation, authentication, styling primitives, spending controls, token snapshots, simple reminders, and shared browser. The largest new subsystem is a persistent mixed Watchlist with observations, conditional checks, and durable updates. Reproducing the layouts is frontend work; making the displayed prices, changes, schedules, and money figures true requires backend work.

## Recommended implementation structure

Use one Watchlist item abstraction for identity and presentation, with kind-specific source details. Keep a saved item independent from a monitoring subscription: an article can remain saved forever without scheduled checks or charges. Existing reminders should be linked/projected into the list rather than duplicated into another scheduler.

An observation belongs to an item and records a successful observed value, source, time, currency/basis and provenance. A watch describes what to check, its threshold, next run, expiry and capacity. A change event records why an update was shown or sent. These responsibilities need durable data and versioned contracts; exact table/file boundaries can follow the repository's preference for a small complete vertical slice.

For websites, saving any valid public URL is broadly achievable. Reliably checking any arbitrary website is a different promise. The full flight and shoe examples require actual working data retrieval, not just bookmark cards. Identify and verify supported sources; report unsupported/needs-attention states honestly. Current unattended browser restrictions and shared-Chrome human control must remain explicit architectural constraints.

## Build sequence toward the full target

1. **Contracts and shared items:** identity, persistence, API, observation/watch/update states, source links and conversation attachment. Include token, product, flight, link and reminder cases in the contract.
2. **Responsive shell and complete saved-item flow:** Home chat, money summary with currently supported values, two-item navigation, recent chats, mixed Watchlist, mobile details and optional desktop pane.
3. **Agent interaction:** save/read items, inspect selected context, render typed cards, review a watch proposal, create/edit reminders and summarize recorded changes.
4. **Monitoring:** token refresh, supported merchant and flight data retrieval, six-hour intervals, expiry, pause/resume, threshold comparisons, deduplicated alerts and durable unread updates.
5. **Money details and polish:** broader holdings valuation and P&L, reliable budget readout, source thumbnails, responsive/motion/accessibility refinement.

These steps are a sequence, not a reduction of scope. The full images are only functionally realized when the actual flight/shoe checks, price history, watch lifecycle, context attachment and money semantics work alongside the layout.

## Verification and acceptance evidence

For this investigation, ran: `bun test apps/server/src/schedule-routes.test.ts apps/server/src/schedules.test.ts apps/server/src/trading/birdeye.test.ts apps/server/src/trading/launches.test.ts`

**41 tests passed, 0 failed; 183 assertions.** These test local/fake-provider behavior for existing primitives. They do not prove live provider access or the new target UI.

Existing e2e suites cover navigation at multiple widths, chat history, paid browsing, and mocked reminder list/cancellation. No Watchlist flow exists to test. Some current motion tests explicitly assert old count-up/slide/pause behavior and should be revised to test the intended design, while retaining useful accessibility and input checks.

Acceptance for implementation:

- At 390px mobile and the desktop reference width, compare screenshots against both concepts; also test 320px and tablet layout, keyboard focus, safe areas, contrast and reduced motion.
- Save all four item kinds, reload, search/filter, edit/archive and open details; ownership must hold across two different users.
- Ask about a selected item, change threads, reload history, and verify the correct item/snapshot remains attached without inventing user authorization.
- Make a known product/flight quote change trigger one recorded update on the same variant/itinerary; failures and changed currency do not produce false alerts.
- Verify six-hour scheduling, expiry, pause/resume, concurrent workers, crash recovery and alert deduplication.
- Show next check/last successful check accurately and preserve unread updates offline/across restarts.
- Create and edit tomorrow's reminder in the user's timezone; verify delivered versus failed delivery.
- Review paid watch capacity once; replay/retry does not double-charge. Preserve existing approval, freeze, receipts and browser takeover.
- Reconcile displayed available funds against balances/reservations and holdings against actual valued inventory. Test missing basis, unknown prices and external transfers before showing P&L.
- Run `bun run check:fast` during implementation, `bun run check` before completion, and `bun run e2e` for the visible changes. Exercise representative live token and website retrieval separately; mocked tests cannot establish real data coverage.

No app source changed during this assessment. The worktree already contains unrelated in-progress email, OAuth, wallet and history changes; implementation should preserve and integrate them.
